## 1. 과제 목표 (6대 핵심 역량 기술 해설)

### Q1. 시계열 데이터를 분석하고, 요약 정보를 만들어 서비스에서 활용하는 흐름을 설명할 수 있는가?
* **답변:**
  1. **수집 및 저장:** `(date, value, memo, category)` 형태의 120개 시계열 데이터가 Firestore `data` 컬렉션에 날짜순으로 저장됩니다.
  2. **통계 분석 및 추세 도출 (`analytics_service.py`):**
     - 전체 데이터의 시작일~종료일로 **기간(period)**을 계산하고, 누적합(`total`), 평균(`average`), 최댓값(`max`), 최솟값(`min`), 최신값(`latest_value`)을 집계합니다.
     - 최근 7개 데이터의 평균과 전체 평균을 비교하는 이동평균 대비 증감율 공식을 통해 **추세(trend, 예: "상승 추세 (+15.2%)")**를 자동 판정합니다.
  3. **서비스 활용:**
     - 프론트엔드 대시보드 상단 4대 메트릭 카드 및 Canvas 차트에 실시간 시각화됩니다.
     - AI 대화 시 시스템 프롬프트(System Prompt)에 주입되어 LLM이 사용자의 실제 실적을 인용한 정확한 답변을 생성하는 기반 컨텍스트로 활용됩니다.

### Q2. FastAPI 프로젝트를 라우터/서비스 등으로 분리해 구성한 기준을 설명할 수 있는가?
* **답변:**
  - **관심사의 분리(Separation of Concerns, SoC)**와 **단일 책임 원칙(SRP)**을 기준으로 계층을 명확히 분리했습니다:
    - `main.py`: 애플리케이션 진입점, CORS 미들웨어, 헬스체크, 정적 파일 서빙 및 라우터 등록만 담당.
    - `routers/`: HTTP 요청 수신, 쿼리/바디 파라미터 바인딩, HTTP 상태 코드(200, 201, 404) 반환 등 **전송 계층(Transport Layer)** 담당.
    - `services/`: 순수 비즈니스 로직(통계 알고리즘, LLM 호출, DB I/O 추상화)을 담당하여 웹 프레임워크와 비즈니스 로직을 분리.
    - `models/`: Pydantic 기반 입출력 데이터 규격 및 타입 검증 전담.
    - `config.py`: 환경변수 관리 및 외부 클라이언트(Firebase, Gemini) 초기화 담당.

### Q3. Pydantic을 활용해 요청 데이터 검증을 적용한 이유와 방식을 설명할 수 있는가?
* **답변:**
  - **이유:** 클라이언트로부터 들어오는 잘못된 형식(예: 음수값, 누락된 날짜, 잘못된 필드명)을 런타임 이전에 차단하여 DB 무결성을 지키고, 자동 Swagger 문서화 및 타입 힌팅을 얻기 위함입니다.
  - **방식 (`models/data_model.py`):**
    - `DataCreate`: 필수 필드(`date`, `value`, `memo`)와 기본값(`category="일반"`)을 선언하고 `Field(..., examples=[...])`로 명세화.
    - `DataUpdate`: 부분 수정을 허용하기 위해 모든 필드를 `Optional`로 선언.
    - 유효하지 않은 입력 시 FastAPI가 자동으로 `422 Unprocessable Entity` 에러와 세부 원인을 JSON으로 반환하도록 구성.

### Q4. Firestore에 데이터를 저장하고 CRUD로 다루는 방법을 설명할 수 있는가?
* **답변 (`services/firestore_service.py`):**
  - **Create:** `db.collection("data").document(doc_id).set(data_dict)`을 호출하여 고유 ID로 도큐먼트 생성.
  - **Read:** 단건은 `.document(id).get()`, 목록은 `.order_by("date").stream()`을 통해 날짜순 정렬 조회.
  - **Update:** `doc_ref.update(update_fields)`를 통해 변경된 필드만 부분 업데이트.
  - **Delete:** `doc_ref.delete()`로 도큐먼트 삭제.
  - **대량 시딩:** `db.batch()`를 활용해 120개 데이터를 500개 단위 배치로 원자적(Atomic) 일괄 커밋(`seed_data.py`).

### Q5. “데이터 요약을 시스템 프롬프트에 주입하는 방식(컨텍스트 주입)”의 원리를 설명할 수 있는가?
* **답변 (`services/ai_service.py`):**
  - **원리:** LLM은 사전에 학습되지 않은 사용자의 개인 데이터나 실시간 상태를 알 수 없습니다. 따라서 사용자가 질문하기 전, 백엔드가 DB에서 최신 데이터 요약본(기간, 평균, 최고치, 트렌드)을 조회하여 LLM의 **System Instruction(시스템 지시어)** 영역에 텍스트 형태로 삽입(Injection)한 뒤 사용자 질문과 함께 LLM에 전달하는 원리입니다.
  - 이를 통해 모델 파인튜닝(Fine-tuning) 없이도 최신 데이터에 기반한 정확하고 환각 없는(Fact-grounded) 답변을 도출합니다.

### Q6. 배포 환경에서 CORS/환경변수/키 관리가 왜 필요한지 설명할 수 있는가?
* **답변:**
  - **CORS:** 프론트엔드 도메인(`vercel.app`)과 백엔드 도메인(`onrender.com`)의 오리진(Origin)이 서로 다르므로, 브라우저의 동일 출처 정책(SOP)에 의해 차단됩니다. 백엔드의 `CORSMiddleware`에 허용 도메인 화이트리스트를 등록해야 안전하게 통신할 수 있습니다.
  - **환경변수 및 키 관리:** `GEMINI_API_KEY`, `FIREBASE_SERVICE_ACCOUNT_JSON` 같은 보안 자격증명이 GitHub 공개 레포지토리에 커밋되면 악용 및 비용 폭탄이 발생합니다. `.gitignore`로 소스코드에서 배제하고 배포 플랫폼(Render/Vercel)의 암호화된 Secret 환경변수로 격리 주입해야 합니다.

## 3. 평가질문 2: 아키텍처 및 계층별 설계 의도

### 1) FastAPI에서 라우터/서비스 등을 어떤 기준으로 분리했는가?
* **라우터 (`routers/`):** HTTP 프로토콜 규격 통제 계층. 엔드포인트 URL 매핑, 상태 코드, 파라미터 유효성 검사 결과 반환만 처리.
* **서비스 (`services/`):** 순수 비즈니스 로직 계층.
  - `analytics_service.py`: 시계열 통계 계산 및 트렌드 분석 알고리즘
  - `ai_service.py`: 프롬프트 템플릿 조립, Gemini API 통신, 도구 호출(Function Calling)
  - `firestore_service.py`: Firestore I/O 캡슐화 및 로컬 In-Memory Fallback 스토리지 제어
* **모델 (`models/`):** 데이터 전송 객체(DTO) 및 유효성 검증 규칙 정의.

### 2) data / conversations 컬렉션 구조를 왜 그렇게 설계했는가?
* **`data` 컬렉션 (단일 레코드 단위):**
  - 구조: `{ id, date, value, memo, category, created_at }`
  - 이유: 시계열 데이터는 기간별 조회, 정렬, 통계 집계, 개별 수정/삭제가 빈번하므로 도큐먼트를 개별 원자 단위로 분리하여 빠른 인덱스 쿼리가 가능하도록 설계.
* **`conversations` 컬렉션 (세션 단위):**
  - 구조: `{ id, title, messages: [ {role, content, timestamp}, ... ], updated_at }`
  - 이유: 대화는 문맥(Context)의 흐름이 중요하므로, 한 세션 내의 메시지 배열을 하나의 도큐먼트로 묶어 단 1회의 Read 요청으로 대화 전체를 빠르게 불러올 수 있도록 설계.

### 3) 요청/응답 스키마(Pydantic)를 어떤 기준으로 정의했고 검증을 어디에 적용했는가?
* **정의 기준:** 클라이언트가 보내는 데이터(Request)와 서버가 돌려주는 데이터(Response)의 필드 요구조건이 다르므로 분리 정의.
  - 생성용(`DataCreate`): `date`, `value`, `memo` 필수.
  - 수정용(`DataUpdate`): 부분 변경을 위해 모든 필드 `Optional`.
  - 응답용(`DataResponse`): 서버에서 생성된 `id`, `created_at` 포함.
* **검증 적용:** 날짜 문자열 포맷, `value`의 float 타입 강제, `order` 쿼리 파라미터의 정규식 패턴(`pattern="^(asc|desc)$"`) 등을 적용하여 비정상 데이터 입력 원천 차단.

### 4) 프론트에서 “데이터 관리/대화 불러오기/채팅” 화면을 어떤 상태 흐름으로 연결했는가?
* **단방향 비동기 오케스트레이션 (`app.js`):**
  - 데이터 변경(추가/수정/삭제) 발생 ➔ `ApiClient` 호출 ➔ 완료 후 `Promise.all([loadSummaryAndChart(), loadDataTable()])`를 통해 요약 메트릭, 시계열 차트, 목록 테이블을 동시 갱신.
  - 대화 세션 클릭 ➔ `currentConversationId` 상태 변경 ➔ `GET /api/conversations/{id}` ➔ 채팅창 DOM 초기화 및 메시지 렌더링 ➔ 이후 질문은 해당 `conversation_id`로 지속 전송.

## 4. 평가질문 3: 컨텍스트 주입 및 운영 보안 정책

### 1) “컨텍스트 주입(요약→시스템 프롬프트)”을 왜 사용했고, 어떤 장단점이 있는가?
* **사용 이유:** LLM에게 최신 데이터 지식을 부여하는 가장 가볍고 정확한 기법이기 때문입니다.
* **장점:**
  1. 고비용의 모델 재학습(Fine-tuning) 없이 즉각적인 실시간 데이터 반영 가능.
  2. 프롬프트에 사실(Fact) 기반 요약본이 명시되므로 환각(Hallucination) 대폭 감소.
* **단점:**
  1. 프롬프트 입력 토큰을 소모하므로 데이터가 방대해질 경우 전체 원본을 다 넣을 수 없음 (→ 따라서 정제된 통계 요약 엔진이 필수적임).

### 2) 데이터 요약(/api/data/summary)을 별도로 둔 이유(책임 분리/재사용성)는?
* **재사용성 (DRY 원칙):** 통계 요약 데이터는 ① 프론트엔드 대시보드 지표 카드 렌더링, ② AI 채팅 시 프롬프트 주입이라는 서로 다른 2개 기능에서 동일하게 필요합니다.
* **책임 분리:** 통계 연산 로직을 단일 엔드포인트/서비스로 캡슐화하여 통계 산출 공식(예: 이동평균 7일 기준)이 변경되더라도 프론트나 AI 모듈의 수정 없이 백엔드 연산부만 독립 수정할 수 있습니다.

### 3) 대화 저장 방식(언제 저장하는지, 어떤 형태로 저장하는지)을 선택한 이유?
* **저장 시점:** 사용자 질문 수신 ➔ LLM 답변 완료 직후 원자적으로 저장. 사용자가 일일이 '저장' 버튼을 누를 필요가 없는 **자동 영속화(Auto-Persistence)** UX 제공.
* **저장 형태:** `{ title, messages: [{role, content, timestamp}] }` 형태의 배열 구조로 저장하여 대화의 시간적 선후 관계를 완벽히 보존.

### 4) 환경 변수를 어떤 이유로 도입했고, 실제로 어떻게 적용했는가?
* **도입 이유:** 보안(Secret Key 유출 방지)과 환경별 격리(로컬 개발 환경과 프로덕션 배포 환경의 URL/키 분리).
* **실제 적용:**
  - `python-dotenv`를 통해 로컬에서는 `.env` 파일 로드.
  - Render 배포 환경에서는 대시보드 Secret Environment(`GEMINI_API_KEY`, `FIREBASE_SERVICE_ACCOUNT_JSON`)를 통해 컨테이너 환경변수로 주입.
  - 소스코드 어디에도 하드코딩된 비밀키가 존재하지 않도록 설계.

## 5. 평가질문 4: 안정성, 확장성 및 장애 대응(Edge Cases)

### 1) 첫 접속 지연(콜드스타트)이 발생했을 때 사용자가 납득할 수 있도록 어떻게 안내/완화했는가?
* **UI 레벨 안내:** 프론트엔드 최상단에 `⚡ 서버를 깨우는 중입니다. 잠시만 기다려 주시면 즉시 모든 기능이 연결됩니다.` 배너를 기본 배치하고, 서버 헬스체크(`/api/health`) 통신 완료 시 자동으로 숨김 처리.
* **연결 상태 실시간 뱃지:** 상단 헤더에 `[서버 연결 중... (노란 펄스)]` ➔ `[API 온라인 (초록 불)]` 상태 인디케이터를 제공하여 사용자가 시스템 상태를 명확히 인지하도록 유도.

### 2) CORS가 왜 발생했고, 어떤 설정으로 해결했는가?
* **발생 원인:** Vercel(`https://codyssey-m1-2.vercel.app`)과 Render(`https://codyssey-m1-2.onrender.com`)의 도메인(오리진)이 달라 브라우저의 동일 출처 정책(SOP)에 의해 API 호출이 차단됨.
* **보안 모범 사례 적용 (와일드카드 `*` 지양):**
  - 단순 개발 편의를 위해 `allow_origins=["*"]`를 사용하는 것은 악의적인 제3자 웹사이트에서 사용자의 인증 세션/데이터를 탈취할 수 있는 **CORS 보안 취약점(CORS Misconfiguration)**을 초래하므로 지양해야 합니다.
  - 특히 `allow_credentials=True`(쿠키/인증 헤더 포함) 옵션과 `allow_origins=["*"]`는 표준 브라우저 스펙상 충돌하여 에러를 발생시킵니다.
* **해결 설정 (`main.py` & `.env`):**
  - `settings.ALLOWED_ORIGINS` 환경변수를 통해 **실제 배포된 Vercel 도메인(`https://codyssey-m1-2.vercel.app`)과 로컬 개발 주소만 엄격히 화이트리스트**로 지정.
  - HTTP 메서드 역시 `["GET", "POST", "PUT", "DELETE", "OPTIONS"]`만 명시적으로 제한 허용.
  ```python
  app.add_middleware(
      CORSMiddleware,
      allow_origins=settings.ALLOWED_ORIGINS, # 명시적 화이트리스트 도메인만 허용
      allow_credentials=True,
      allow_methods=["GET", "POST", "PUT", "DELETE", "OPTIONS"], # 최소 권한 원칙
      allow_headers=["Content-Type", "Authorization", "Accept"],
  )
  ```

### 3) 사용자 입력을 그대로 저장/전달할 때의 위험과 최소 대응은?
* **위험:**
  1. **XSS (Cross-Site Scripting):** 악성 스크립트가 포함된 메모가 웹 화면에 실행되는 위험.
  2. **프롬프트 인젝션 (Prompt Injection):** AI에게 시스템 지침을 무시하도록 유도하는 악성 입력.
* **대응책:**
  - 프론트엔드: `escapeHtml()` 함수를 구현하여 모든 사용자 입력과 메모 텍스트의 특수문자(`&`, `<`, `>`, `"`, `'`)를 HTML 엔티티로 치환하여 DOM에 삽입.
  - 백엔드: Pydantic 타입 검증 및 시스템 프롬프트 상단 격리 지시어 배치.

### 4) 데이터가 수만 건으로 늘어나거나 요약 기준이 바뀌면 어디를 어떻게 수정할 것인가?
* **수정 위치:** `services/analytics_service.py` 내부 로직만 수정하면 됨.
* **구체적 확장 방안:**
  1. **슬라이딩 윈도우(Sliding Window):** 전체 데이터를 메모리에 올리지 않고, Firestore 쿼리에서 `.where("date", ">=", thirty_days_ago).limit(100)` 조건을 걸어 최근 30일 데이터만 슬라이싱하여 요약.
  2. **배치 사전 집계(Pre-aggregation):** 데이터 추가 시 일일/월별 통계를 트리거로 사전 계산하여 별도 메타 도큐먼트에 캐싱하는 방식으로 $O(1)$ 조회 성능 확보.
